# Provider integrations — URL contract

Wearable providers (Garmin, Oura) link to an Anamna account through OAuth2 and push data to
us through webhooks. This document is the contract: the URLs to paste into each provider's app
registration, the endpoints this application serves, and the configuration each side needs.
Endpoint skeletons live in [src/anamna/integrations.py](../src/anamna/integrations.py);
route handlers in [src/anamna/web/app.py](../src/anamna/web/app.py) under
`# --- Provider integrations ---`.

The path scheme is uniform on purpose: `/integrations/<provider>/<role>`. Adding a provider later
(Withings, Fitbit, …) reuses the same shape and the same middleware exemptions.

## URLs to register — copy-paste block

### Garmin — three tiers, two code paths

Garmin's Connect Developer Program reopened on 2026-10-21 with three tiers
([overview](https://developer.garmin.com/gc-developer-program/overview/)):

| Tier | Delivery | History | Users | Here |
|---|---|---|---|---|
| **Personal** | pull only | whatever the account holds | the key owner only | `garmin_personal.py` — each person pastes their own key on `/profile` |
| **Starter** | push only | none | limited | `garmin.py` — OAuth2 + webhook |
| **Enterprise** | push or ping | ~1 month, once per type | unlimited | `garmin.py` — same, plus backfill |

**Personal API** keys start with `GCDC_` and are created by the account owner at Garmin Connect
→ Settings → Personal API (`connect.garmin.com/app/settings/personalApiToken`), valid 30 days to
one year. They are read-only and, per Garmin's terms, for applications the owner operates for
their own use — so nobody stores anyone else's key. No registration is needed on Garmin's side;
the operator only switches the feature on (`garmin_personal_enabled`, below).

**Starter / Enterprise** need an app in the developer portal and these values:

| Registration field | Value |
|---|---|
| OAuth2 redirect URI | `https://<your-host>/integrations/garmin/callback` |
| Endpoint configuration — every summary type, **push** | `https://<your-host>/integrations/garmin/webhook` |

Garmin's endpoint tool (`apis.garmin.com/tools/endpoints`) takes one URL per summary type. Point
**all** of them at the single `/webhook` URL — the payload's top-level key names the type. Push and
ping both work (a ping's `callbackURL` is fetched only if it is on `apis.garmin.com`); prefer push.
Leave `epochs`, `activityDetails` and `activityFiles` **disabled**: they are intraday samples and
FIT files this app archives but does not chart, and activity details can reach 100 MB. One Garmin
app has one URL per type, so the same credentials cannot feed both this app and OpenWearables —
pick one receiver per app.

### Oura — [cloud.ouraring.com/oauth/applications](https://cloud.ouraring.com/oauth/applications)

| Registration field | Value |
|---|---|
| Redirect URI | `https://<your-host>/integrations/oura/callback` |
| Redirect URI (local development) | `http://localhost:8000/integrations/oura/callback` |

Oura allows several redirect URIs per application — register both. The webhook callback URL is
**not** entered in the Oura portal; subscriptions are created by us through their API
(`POST https://api.ouraring.com/v2/webhook/subscription`, authenticated with
`x-client-id`/`x-client-secret` headers) and carry:

| Subscription field | Value |
|---|---|
| `callback_url` | `https://<your-host>/integrations/oura/webhook` |
| `verification_token` | generated by us, stored in `app_settings` |

Note the Oura application is limited to 10 connected users until Oura approves it; the approval
form also asks for the redirect URI, so keep it stable.

## Endpoints this application serves

Browser-facing (session auth, CSRF on POST):

| Method + path | Purpose |
|---|---|
| `GET /integrations/{provider}/connect` | Start the OAuth flow: mint `state` (+ PKCE verifier for Garmin), persist them, 303 to the provider's authorize URL. A GET navigation, not a form POST — Chrome checks `form-action` against every redirect hop of a form submission, and the provider's SSO chain crosses hosts |
| `GET /integrations/{provider}/callback` | Provider redirects the browser back with `?code=&state=`. Validate state, exchange code for tokens, store the connection, redirect to `/profile` |
| `POST /integrations/{provider}/disconnect` | Revoke at the provider where supported, delete the stored connection. For Garmin this calls `DELETE …/user/registration` (Garmin requires it) and deletes what Garmin delivered |
| `POST /integrations/garmin/sync` | Process stored Garmin deliveries and retry a paused backfill. Garmin forbids ad-hoc pulls, so it cannot fetch on demand |
| `POST /integrations/garmin/personal` | Save a Personal API key: shape check, then a real token exchange; nothing is stored if Garmin refuses it |
| `POST /integrations/garmin/personal/sync`, `…/remove` | Re-read the last 30 days now; forget the key (data stays — it is the person's own, pulled with their own key) |

Provider-facing (no session, no CSRF — exempted in middleware, verified by signature/token instead):

| Method + path | Caller | Behaviour |
|---|---|---|
| `GET /integrations/oura/webhook` | Oura, once, at subscription creation | Echo the challenge: request carries `?verification_token=&challenge=`; if the token matches ours, answer `200 {"challenge": "<challenge>"}` |
| `POST /integrations/oura/webhook` | Oura, ~30 s after a ring syncs | Verify `x-oura-signature` (HMAC-SHA256 of `x-oura-timestamp` + raw body, client secret as key, uppercase hex). Store the event, answer `200` immediately; fetching the object is a separate later step |
| `POST /integrations/garmin/webhook` | Garmin, on device sync | 404 until Garmin credentials exist. Garmin does not sign deliveries; the `garmin-client-id` header must equal our client id (constant-time compare, 401 otherwise). Store the payload, answer `200` within Garmin's 30 s, process on a thread. Deliveries repeat: processing is idempotent |

## Configuration

Client credentials are app-level, not per-user. They follow the Paperless pattern: an
`app_settings` row wins once stored (even when empty), and an environment variable seeds an
unconfigured instance (exported into the server's environment, or set on the container; same rule
as `ANAMNA_AGENT_TOKEN`). A provider with no client id + secret is invisible in
the UI and its routes answer 404.

| `app_settings` key | Env fallback | From |
|---|---|---|
| `garmin_client_id` / `garmin_client_secret` | `ANAMNA_GARMIN_CLIENT_ID` / `..._SECRET` | Garmin developer portal, Starter or Enterprise app |
| `garmin_personal_enabled` | `ANAMNA_GARMIN_PERSONAL` | `1` offers the Personal-key card on `/profile`; each person brings their own key |
| `oura_client_id` / `oura_client_secret` | `ANAMNA_OURA_CLIENT_ID` / `..._SECRET` | Oura application page |
| `integrations_public_url` | `ANAMNA_PUBLIC_URL` | the deployed origin, for example `https://<your-host>` |
| `oura_verification_token` | — | minted automatically when the first Oura account connects |

`integrations_public_url` exists because the redirect URI must match the registered string exactly
and `request.base_url` behind a TLS-terminating proxy or tunnel reports `http://`; unset, the app falls back to
`request.base_url`, which is correct for local development. Read the minted Oura verification token
(needed once, when creating the webhook subscription) with:

```bash
uv run python -c "import sqlite3;print(sqlite3.connect('data/anamna.sqlite3').execute(\"SELECT value FROM app_settings WHERE key='oura_verification_token'\").fetchone())"
```

## Oura data flow (implemented)

`src/anamna/oura.py` owns everything after the OAuth handshake. Every write is a **windowed
recompute** (`sync_range`): fetch one data type for a date window, rebuild the daily rows for the
metric keys that type owns, upsert on the natural key `(owner, "Oura", metric_key, day)`, and
delete Oura days in the window the API no longer reports. Backfill (on connect, from 2015-10-01),
webhook events (window around the changed document; deletions widen to 90 days) and the profile's
"Sync now" button (last 30 days) are all that one code path.

| Oura data type | Becomes |
|---|---|
| `sleep` | `sleep_duration/_deep/_rem/_core/_awake`, `time_in_bed`, `sleep_efficiency`, `resting_heart_rate`, `heart_rate_variability`, `respiratory_rate` — periods summed per day, `rest`/`deleted` types excluded, HRV/breath/efficiency from the longest period |
| `daily_sleep` / `daily_readiness` / `daily_activity` | `sleep_score`; `readiness_score`, `temperature_deviation`; `steps`, `active_energy`, `resting_energy` (total − active), `activity_score`, `moderate_activity`, `vigorous_activity` |
| `daily_spo2` / `daily_stress` / `daily_cardiovascular_age` / `vo2_max` | `blood_oxygen`, `breathing_disturbance_index`; `stress_high_time`, `recovery_high_time`; `cardiovascular_age`, `pulse_wave_velocity`; `vo2_max` |
| `heartrate` (pull-only, no webhook) | `daily_heart_rate` day aggregates (avg/min/max), fetched in monthly chunks alongside every sync |
| `workout`, `session`, `enhanced_tag` | `device_workouts` rows (activity, duration, kcal, km) and "Oura tag" `device_events` |
| `daily_resilience`, `sleep_time`, `rest_mode_period`, `meal`, `tag` | retained raw in `provider_events` only — enums and recommendations, not measurements |
| `ring_configuration`, `personal_info` | the profile card (ring model/size/firmware) and `external_user_id` |

Proprietary scores and vendor indices carry **no reference bands on purpose** — they render with
the "no published range" explainer, the same honest answer the existing Oura score keys give.

Tokens: Oura refresh tokens are single-use; `oura.py` rotates the pair under a per-user lock and
stores it before use. A refused refresh (400/401) marks the connection `reauthorize`, which the
profile card surfaces with a reconnect button; rate limits and outages do not.

Webhook subscriptions: `ensure_subscriptions` creates one per (data type × create/update/delete),
renews any expiring within 7 days, and replaces subscriptions pointing at a stale callback. It runs
after a connect, on every "Sync now", and at most daily during webhook processing. **It only works
where Oura can reach the configured public URL** — the challenge GET must be answered by the same
instance holding `oura_verification_token`, so subscriptions are effectively created by the
deployed instance; a local machine without a public address shows "Automatic updates: off" and
relies on manual sync.

## Garmin data flow (implemented)

Both tiers write the same device tables as the Garmin file importer, through one set of mappers
and writers in `garmin.py`, so `/devices` needs nothing. Units go through
`devices.units.convert_quantity` into the catalog's unit for each key (a test asserts every key
folds to the catalog spelling through `canonical_unit()`). Scale and blood-pressure readings use
the file importer's source names (`Garmin Index Scale`, `Garmin Connect user entry`,
`Garmin Connect blood pressure`), so a reading present in an export *and* the API is one row.

**Business tier — mirror, then rebuild.** Every delivered summary is upserted into
`garmin_summaries` (latest copy wins; one-per-day types are keyed by calendar date because a
revision may carry a new `summaryId`; activities by `activityId`, so a
`manuallyUpdatedActivities` edit replaces the original). Each touched (type, day) is then rebuilt
from the mirror and this envelope's rows the rebuild no longer produces are deleted.

| Garmin summary | Becomes |
|---|---|
| `dailies` | `steps`, `walking_running_distance` (m→km), `flights_climbed`, `active_energy` (excludes BMR), `resting_energy` (BMR), `moderate_activity`/`vigorous_activity` (s→min), `resting_heart_rate`, `daily_heart_rate` (avg with Garmin's own min/max), `stress_level` (−1 = not enough data, dropped) |
| `sleeps` | `sleep_duration` = deep+light+rem (awake excluded), `sleep_deep/core/rem/awake`, `time_in_bed` = `durationInSeconds`, `sleep_score` |
| `hrv` / `stressDetails` / `userMetrics` / `skinTemp` | `heart_rate_variability_rmssd`; `body_battery_high/low` (negatives dropped); `vo2_max`, `fitness_age`; `temperature_deviation` |
| `bodyComps` | `body_weight`, `bone_mass`, `muscle_mass` (g→kg), `body_mass_index`, `body_fat_percentage`, `body_water_percentage` (0 = not measured, dropped) |
| `bloodPressures` | `systolic/diastolic_blood_pressure`, `blood_pressure_pulse` |
| `pulseox` / `allDayRespiration` | `blood_oxygen` (50–100 %), `respiratory_rate` (4–60/min) day averages; dropouts are not readings |
| `activities` (+ edits), `moveIQActivities`, `mct` | `device_workouts`; "Garmin Move IQ" and "Menstrual cycle" events (predicted cycles skipped) |
| `epochs`, `activityDetails`, `activityFiles`, `healthSnapshot` | archived raw in `provider_events` only |

Lifecycle: a `deregistrations` notice deletes the connection and everything Garmin delivered
(a notice received *before* the current connection was made is stale and ignored);
`userPermissionsChange` updates the stored permissions and deletes the withdrawn scope's data
(`HEALTH_EXPORT` → health types, `ACTIVITY_EXPORT` → workouts and Move IQ, `MCT_EXPORT` →
cycles). An in-app disconnect calls `DELETE …/user/registration` and deletes the same data. Rows
from a Garmin *file export* the person imported are a different envelope and are never deleted.
Backfill (Enterprise only) asks once per type for the last 30 days; 202/409 count as done,
400/403/412 as unavailable for this tier or consent, anything else pauses until the next
"Check for new data". A delivery whose ping cannot be resolved stays pending — Garmin never
redelivers a 200 — and the scheduler retries it every 15 minutes.

**Personal tier — windowed recompute** (the Oura pattern). Datasets and their per-request limits
from Garmin's OpenAPI: daily summaries (365 days), sleep (31), HRV (366), weight (3650 tested),
activity search (paged), fitness age (one "as of" value). Backfill reads daily summaries from 2008
to find the first day a watch was worn and only asks for sleep and HRV from then (an account with
only a scale costs ~20 requests, not ~240). The scheduler re-reads the last 30 days every six
hours. Garmin's spec says weight is in kilograms; the live API answers **grams** (measured
2026-11-05), and the mapper converts from grams. Not available through a personal key: blood
pressure, VO₂ max, skin temperature — the Garmin file export still covers blood pressure.

## What Garmin requires of an integrator (business tiers)

- **Consent** happens on Garmin's own OAuth screen; track it with `GET …/user/permissions` and the
  `userPermissionsChange` notice. The profile card lists what was shared.
- **Disconnect** must call `DELETE …/user/registration`; handle the `deregistrations` notice that
  follows (and stale ones after a reconnect).
- **Data deletion**: Garmin's specs name no explicit clause; the program agreement reportedly
  requires deletion on termination. This app deletes Garmin-delivered data on deregistration,
  withdrawn permission and in-app disconnect.
- **Webhooks**: HTTPS on standard ports, 200 within 30 s with processing asynchronous, accept
  ≥10 MB bodies (100 MB for activity details): `MAX_EVENT_BYTES` is 100 MB, which is also
  Cloudflare's request cap if you put the app behind it.
- **No pull-only integrations** and no ad-hoc summary calls outside a ping's callback.
- **Production review**: at least two connected users with real device data, deregistration and
  permission endpoints enabled and tested, brand review. Brand guidelines require Garmin data to
  be attributed to "Garmin [device model]" next to the title; rows here carry source "Garmin".
- **Rate limits**: backfill counts days of data — evaluation keys 100 days/minute, production
  10,000 days/minute; one 30-day window per type stays well inside either.

## Storage

Three tables, created by the standard migration path:

- `provider_connections` — one row per (user, provider): tokens, expiry, external user id, scopes,
  status. Cascades from `users` like every other child table.
- `provider_events` — raw webhook arrivals: provider, payload, received/processed timestamps.
  Webhook handlers only ever insert here and return 200; parsing into observations is the
  processing step that comes later and can re-run (idempotent by provider + payload identity).

- `garmin_summaries` (035) — the latest copy of every Garmin business-tier summary, the mirror
  each (type, day) is rebuilt from. Deleted with the person, on deregistration and on withdrawn
  permission.

A Garmin Personal API key is stored in `provider_connections` under provider `garmin_personal`:
the key in `refresh_token` (it is what mints new tokens), the current JWT in `access_token`.

Transient OAuth state (`state`, PKCE verifier) lives in `oauth_states`, keyed by the random state
value, expiring after 10 minutes.
